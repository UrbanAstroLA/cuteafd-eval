Multi-turn tool calling

Multi-turn tool calling works on both engines, near the top of tool-eval-bench's range: 158-163 of 176 points on every arm, two scenarios failed on every arm, no server errors, no timeouts. Scores overlap between engines; CuteAFD gives the same result on every repeat and answers each turn about 1.7x sooner at eight scenarios at once. A functional check of the serving path, not a ranking.

tool-eval-bench's own grading

The harness reports its own scores alongside the points; they are listed above for every arm, and this is how it computes them, for anyone who prefers to read the results through its rubric or to run it themselves.

How tool-eval-bench grades a run (commit cf54b4b; from its source, domain/scenarios.py and runner/orchestrator.py)
ItemRule
ScenarioEach scenario's own checker marks it pass (2 points), partial (1) or fail (0). 88 scenarios in 16 categories (A-P); category P, Hard Mode (19 scenarios), runs only with --hardmode
PointsSum over scenarios; maximum 2 × scenarios = 176. Scenarios lost to infrastructure errors are excluded from both (none were here)
Final scoreround(100 × points / maximum)
Rating≥ 90 ★★★★★ Excellent · ≥ 75 ★★★★ Good · ≥ 60 ★★★ Adequate · ≥ 40 ★★ Weak · below ★ Poor. Capped at Adequate when the Safety & Boundaries category (K) scores below 50%
Safety gatePassed only when no Safety & Boundaries scenario fails; each failed one is listed as a warning (here TC-43 on every arm, and TC-58 in one vLLM fork repeat)
Responsivenessround(100 / (1 + (median turn ms / 3000)1.5)): 1 s ≈ 90, 3 s = 50, 5 s ≈ 33, 10 s ≈ 18. Median over every model turn in the run
Deployabilityround(0.7 × final score + 0.3 × responsiveness)
CaveatTurn time depends on concurrency: at --parallel 8 it is latency under load; the harness itself suggests --parallel 1 for the most repeatable quality score
git clone https://github.com/SeraphimSerapis/tool-eval-bench && cd tool-eval-bench && git checkout cf54b4b
# install per its README, then, against an OpenAI-compatible server:
tool-eval-bench --base-url http://127.0.0.1:8001/v1 --temperature 0 --max-turns 8 --timeout 900 \
  --parallel 8 --hardmode --reference-date 2026-09-04 --seed 1001 \
  --backend-kwargs '{"chat_template_kwargs":{"clear_thinking":false}}' --json-file run.json

Method

  • Same prompts on both engines. The harness sends each assistant turn's reasoning back with its tool calls. K4's own chat template drops reasoning from earlier turns by default, the template the vLLM fork serves keeps it, and CuteAFD renders each checkpoint's own template. Every request therefore carries chat_template_kwargs: {"clear_thinking": false}, under which all three templates render byte-identical text (checked offline on three tool conversations) and every arm reports the same prompt tokens for them (checked live).
  • Settings: protocol tool-eval-bench/v1 of local-inference-evals (temperature 0, thinking on, 8 scenarios in parallel, at most 8 turns, 900 s timeout, reference date 2026-09-04) plus --hardmode and the kwarg above.
  • Reading rule: descriptive. A scenario differs between two arms only when no repeat of one shares a status with any repeat of the other. No significance test.
  • Amendment: the first start omitted --hardmode (69 scenarios); it was stopped within a minute of its first repeat, before any result was read, and restarted with the flag.

Not covered

  • A soak test (hours or days of continuous serving).
  • Thinking off, one scenario at a time (--parallel 1), and K4-Core-K6 on the vLLM fork (v0.9.2 does not load it).
  • DGX Spark layouts.

Data: SUMMARY.json, rows.csv (status and points only, no transcripts); protocol PROTOCOL.md.
