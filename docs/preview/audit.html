Review of the K3.25 analysis (2026-10-27)

Rendered from results/2026-10-26-cuteafd-vs-vllm/AUDIT-2026-10-27.md.

Reviewer: a separate reviewer who did not run the measurements; read-only. CPU only: no GPU, no requests to :8001, no docker exec. Recomputations ran in docker run --rm --network none containers of local images (v0.9.2 image for numpy; CuteAFD image for tokenizers). The recomputation scripts are not published. Bootstraps I ran are window-cluster percentile bootstraps (5,000 draws, numpy RNG), so their limits differ from the scorer's SplitMix64 ones in the last digit.

---

1. Summary

The instruments are sound. The scorer port, the capture plumbing, the T driver and the summary script reproduce. The precision difference holds: C1 is further from the reference than vLLM on P-B generated rows, it survives the multiplicity and leave-one-out checks below, and C1's NLL is higher at every context bucket.

Four statements in the write-up go further than the data:

  1. Why vLLM varies run to run (cause misattributed). It is not batching or speculation. The data show the variation starts at the second prefill chunk. At 8-16K, vLLM's run-to-run divergence is about two thirds of the cross-engine divergence. The headline magnitudes therefore depend on which vLLM run is used as the baseline.
  2. "Located at 8-16K / grows with context" cannot be separated from content. The 8-16K bucket is block B (long code reading). Within block A, the only block present at every length, the KL gap is flat.
  3. The FP8 mechanism story leaves out several real differences between the engines' arithmetic. F1a also changes the KDA split path as well as KDA precision.
  4. Q2's sub-results rest on 3 clusters and one outlier window.

In Block T, the scheduling explanation holds and can be quantified. Streams that decode without prefill interleaving decode at the same speed on both engines. At 32K/128K the aggregate figure is mostly a prefill measurement.

In Block L, the "terminal loop" flags on code come from the detector counting the answer re-stating code drafted in the reasoning; they are not loops.

I2. The claim of identical inputs does not hold for two Block T details.

  • Nonces differ between engines. block_t.py:20 says requests "pair across engines". The nonce salt is label:time_ns (block_t.py:213), so 0 of 1,008 paired requests share a nonce: every prompt differs in its first line between engines. Seeds still pair, but at temperature 1.0 with two different samplers they do not pair the outputs either.
  • 128K code prompts differ by 24 tokens. All 24 C1 requests at 128K code report 131,096 / 131,095 prompt tokens against the expected 131,072 / 131,071; vLLM matches the expectation. Those prompts (vLLM source) contain literal <think> once and </think> 11 times (checked in stage0/prompts/T/code/128k/p*.json). vLLM's chat path tokenizes them as special tokens; CuteAFD tokenizes them as text. So A2's "thinking on gives both engines the same prompt" (PROTOCOL-DRAFT.md:168-172) does not hold for those cells: vLLM's model sees 11 end-of-thinking control tokens inside the user turn.
  • Impact. Negligible for throughput. It is a stack difference: control-token strings in user text are parsed as control tokens on vLLM.

  • Clustering. The 12 B windows have distinct prompts (prompt_sha256) but similar start offsets (10,790-12,877). Whether they share a source repository or session is not recorded in windows.json; if they do, the effective cluster count is lower. Unverified.

U2. The mechanism inference ("FP8 projections, head and KDA") omits several known differences, and F1a is not a clean ablation.

  • What is right. The protocol's arithmetic table (PROTOCOL-DRAFT.md:33-40) matches the resolved launch. In run-family.sh:2003-2006 and :2061-2064, auto gives row128 KDA and an FP8 head on every layout. The F1 dry-runs confirm it: f1a and f1b raise weight bytes and shrink the pool (local/logs/dry-run-f1a.log vs dry-run-score.log).
    • Note: docs/models/glm5_flash.md:161-166 says the two-GPU head split defaults to BF16 KDA and head. That doc and the code differ on this point.
  • Omitted differences between the engines' arithmetic or geometry (found in source and logs, not measured):
    • DSA indexer. CuteAFD keeps BF16 key/gate rows (keys, forced on a head split; dry-run-score.log:1). vLLM uses FP8 index-K with the B12x kpool top-k (prior audit phase1-indexer-selection.md:31; VLLM_USE_B12X_KPOOL_INDEXER=1). This difference runs in CuteAFD's favour for precision. The indexer engages only past about 2K tokens, which is exactly where any context-dependent gap would appear. Selection and tie handling differ too (22az).
    • Attention placement. CuteAFD uses context: MLA split by token across both GPUs, with a cross-GPU partial-softmax merge (dry-run-score.log:61). vLLM uses split:25: whole MLA layers owned by one GPU, unsharded (start.sh:41-45).
    • KDA split path. On CuteAFD, --kda-output-shard --kda-prefill-expanded (run-family.sh:2012-2017).
    • Prefill geometry. vLLM uses 2,045/2,045/262 chunks aligned to 4,352 (b08.steps.jsonl), and the scored rows straddle chunk boundaries. CuteAFD prefills context in 4,096-row lanes, then scores the 512 rows through the scoring path.
    • Logit precision. vLLM's logits are BF16 before log-softmax (logits_dtype: torch.bfloat16 in every steps.jsonl). Its head output is rounded too; it is not exact BF16-head arithmetic.
    • Prefill-shaped scoring measures CuteAFD's W8A8 prefill GEMMs. Decode and verify rows in serving do not use W8A8 activations; prompt KV written during prefill does carry the effect.
  • New evidence, a cheap mechanism clue. CuteAFD's distributions are systematically flatter (ee2.py, teachH.py, gen rows):

The teacher bound is top-1024 plus the tail as one bucket. Excess entropy over the teacher is +17% for C1 and +5% for V1. This explains why the P-B NLL gap (+0.0168) is about 6x the KL gap: the panel text was generated greedily (windows.json recipe.temperature = 0), so NLL rewards sharpness.   • F1a is confounded. GLM5_FLASH_KDA_FP8=off also removes --kda-output-shard --kda-prefill-expanded (run-family.sh:2012-2017: added only when kda_fp8 != off). It reverts to the half-K BF16 partials path, whose documented cost is about KL +0.0008 and a top-1 loss (run-family.sh:1981-1986). The discovery notes this (discovery-cuteafd-fidelity.md:496), but FOLLOWUPS.md:13 describes F1a as a pure precision switch. A null or adverse F1a result would be uninterpretable.
  • The F1 reading rule is ambiguous (FOLLOWUPS.md:22-23). "Moves … toward V1 by more than the paired interval": interval width, or lower bound? It is also anchored to the single run V1. See I1.

U4. Trailing context rows: "a property of the panel's context rows" is right; the implied reference-side cause is not.

The 12,032 rows are 30 near-copies of one text, so they are effectively one item. The tokenization is canonical: re-encoding gives identical ids in 30 of 30.
  • The rows are hypersensitive. Added checks (checks or confounds not covered at first)

M1. No drift control or in-run telemetry for Block T.

  • Run order. The protocol's CVC drift control (PROTOCOL-DRAFT.md:19) has no declared subset. T ran V then C (V1 18:35-20:35, C1 22:39-00:29), with no repeat of either.
  • Telemetry. There is only a pre-run snapshot: temperature, power limit, memory (t/gpu-before-*.txt: 66/63 °C before V1, 63/61 °C before C1). There are no clocks, power draw or throttle reasons during the runs. On 300 W Max-Q cards, 4 hours apart, this is a real gap.
  • A partial CuteAFD repeat exists. F1-base (f1/speed-F1-base.json, same seeds, scoring launch, 2 hours later) against C1-r1 gives per-cell ratios of 0.96-1.08 on decode and 0.96-1.05 on aggregate. So single-cell noise is about ±4-8%, and T-SUMMARY ratios between 0.95 and 1.08 cannot be read as differences. T-SUMMARY has no intervals, against principle 7 (PROTOCOL-DRAFT.md:20).
  • Desktop on GPU 1. Equal in both runs: 2,045 MiB (V1) and 2,058 MiB (C1) not owned by the engine. Active rendering by a desktop app or the browser during a run cannot be excluded from the logs.

M2. The single-stream speed advantage is plausibly draft policy, and the "code" and "json" labels are misleading.

  • Draft policy differs. vLLM uses a fixed DFLASH_TOKENS=3 (start.sh:61) with a BF16 drafter. CuteAFD uses SPECULATOR_DRAFTS=adaptive (run-family.sh:1700-1707) with an FP8 drafter and W8A8 draft linear (:2074-2076). Acceptance was not recorded, although vLLM's /metrics exposes the speculative-decoding counters.
  • Speedup pattern. 1.16-1.41x on code, json and reasoning against 1.02-1.06 on prose: consistent with deeper drafting on predictable text.
  • The labels. At 1,024 output tokens with thinking on, 0% of code and json requests on either engine left the reasoning (t1.out: content 0% in every code and json cell). So "code" and "json" mean "reasoning about a code or json prompt".
  • Comparable content otherwise. Characters per token agree within about 5%. Reasoning stop rates are 33-58% on both engines.

M3. "As shipped" has undocumented deltas; the full list of launch differences follows.

Block T arithmetic and the scheduling explanation

  • t_summary.py regenerates T-SUMMARY.md byte-identically.
  • aggregate_tok_s = sum of completion tokens / (last token − first send), applied identically to both engines.
  • The scheduling explanation is supported (t2.py). vLLM decode windows overlap other streams' prefill by a median 40-81%, CuteAFD's by 0-51%. Streams whose window overlaps less than 5% decode at the same speed on both engines:

So the 1.5-4x is prefill-first vs interleaved scheduling. It trades against vLLM's earlier first tokens, which is why vLLM's TTFT median is lower at c ≥ 4.

  • At 32K/128K, 71-92% of batch wall time precedes the last first token. The +6-11% aggregate there is mostly CuteAFD's +8-14% batch prefill rate.
  • vLLM prefix cache "0 hits" is confirmed: primer and 3/3 repeats show cached_tokens 0 and TTFT 2.10 s, equal to uncached 8K. CuteAFD shows 8,192 cached and 0.02 s.
    • A candidate mechanism for F2 (inferred): GLM53_DFLASH_BOUNDARY_LOOKUP=0 "drops one block per group" (start.sh:64-67) under --mamba-cache-mode align (start.sh:465). An 8,192-token prompt has one full 4,352 block. F2's lengths of 8,704 and 17,408 test exactly this.
