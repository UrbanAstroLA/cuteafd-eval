Running it: what an operator needs to know

CuteAFD v4.0.0 holds a larger KV pool and starts in about a minute and a half; the vLLM fork takes four to six minutes with its JIT caches kept between starts (established). CuteAFD repeats requests bit for bit; the vLLM fork varies beyond its first prefill chunk (established). CuteAFD reuses repeated prompts; the vLLM fork only in whole large blocks (supported).

Capacity and startup

How much context fits, and how long does a start take?

established CuteAFD v4.0.0 holds a larger KV pool than the vLLM fork on the same checkpoint: 5,799,424 against 4,762,898 tokens on K3.25 and 1,931,264 against 1,377,179 on K4. It is ready in 81-91 s; the vLLM fork in 257-349 s with its JIT caches kept between starts, and 697 s without them. On v3.0.1, CuteAFD needed MAX_CONTEXT_TOKENS=262144 to start K4 on two GPUs.

Why this strength: Recorded on every launch of several runs; the direction is the same in each. Start times are one or two starts per configuration. Scope: GLM-5.3-Flash on two RTX PRO 6000 Blackwell Max-Q (300 W); CuteAFD v3.0.1 and v4.0.0, vLLM fork v0.9.2.

  • context K4-startup-capacity — v3.0.1 on K4
  • context V4-kv-pool-v3 — v3.0.1 pool, with a desktop on one GPU

Repeatability

Does the same request give the same result twice?

established On CuteAFD, yes: scoring rows were bit-identical between passes, launches, days and releases (93,670 of 93,670 rows across launches; 18,286 of 18,286 across days), and tool-calling statuses were the same in all three repeats. On the vLLM fork, rows inside the first 2,045-token prefill chunk repeat exactly and rows beyond it almost never do, and tool-calling status changed between repeats on 8 of 88 scenarios.

Why this strength: Checked in five runs on each engine, with the same result each time. Scope: GLM-5.3-Flash on two RTX PRO 6000 Blackwell Max-Q (300 W); CuteAFD v3.0.1 to v5.0.0, vLLM fork v0.9.2.

Basis (7 findings) and what it does not show
  • supports V3-repeat-cuteafd — v3.0.1
  • supports CS-launch-identity — launches
  • supports AP-cuteafd-cross-day — days
  • supports CP-bf16-repeat — v5.0.0
  • supports V3-i1-chunks — vLLM fork prefill chunks
  • supports K4-determinism — K4
  • supports TC-stability — tool calling

Does not show

  • That either engine is more accurate because of it.
  • Determinism under concurrent load on CuteAFD's scoring path, which takes an exclusive slot.

Prefix cache

Do the engines reuse a repeated prompt?

supported CuteAFD returned a repeated 8,192-token prompt from its cache in 0.017 s. The vLLM fork reused nothing for repeated prompts up to 8,704 tokens and, at 17,408 tokens, reused whole blocks of 4,352 tokens.

Why this strength: One measurement per engine under a frozen protocol (CuteAFD) and a declared follow-up (vLLM fork). Scope: GLM-5.3-Flash on two RTX PRO 6000 Blackwell Max-Q (300 W); CuteAFD v3.0.1, vLLM fork v0.9.2; K3.25.

Basis (2 findings) and what it does not show
  • supports V3-t-cached — repeated 8K prompt
  • supports V3-f2-prefix — vLLM block reuse

Does not show

  • The vLLM fork's opt-in boundary lookup, which was not tested.

Thinking off and control tokens

  • The vLLM fork rendered 147 prompt tokens for enable_thinking true and false alike, and with false returned no separate reasoning (0 reasoning characters; the reasoning arrived in the content); the template has no thinking-off switch and ends every prompt with an open think tag, while CuteAFD renders false as an empty think block. The run therefore used thinking on for every T and L request. V3-think-off (accounting, check)
  • Prompt tokens equal on the chat smoke (26 and 26) and the 1K Block T prompt (1,024 and 1,024); a test prompt with literal <think> tags gave 33 tokens on the vLLM fork and 37 on CuteAFD (29 on both without the tags); both returned reasoning separately. The same seed twice on 3 prompts gave identical text in 1 of 3 on the vLLM fork and 3 of 3 on CuteAFD (cause not examined). K4-smoke (accounting, check)
  • No: 0 of 1,008 paired requests share a nonce first line between the engines (seeds and prompt bodies pair), and the 24 CuteAFD requests at 128K code report 131,096 or 131,095 prompt tokens against 131,072 or 131,071 on vLLM. The audit traces the 24 tokens to literal think-tag strings in those prompts, parsed as special tokens by the vLLM stack and kept as text by CuteAFD. V3-i2-inputs (accounting, check)

Launcher defaults

  • As read in the CuteAFD v3.0.1 launcher: default output limit 4,096 tokens (longer requests are clamped), an unconditional /dev/infiniband device, request logging on by default, listen address 0.0.0.0 under host networking, and swiglu_limit compiled in. V3-obs-launcher (source reading, source reading)
  • The settings are the launcher's defaults, with reasons in its comment: row128 KDA and an FP8 head on both layouts, and on the two-GPU split token-row KDA output ownership to avoid rounding the two GPUs' half-K BF16 partials; the model notes give the speed trade with teacher-forced checks (top-1, KL). The model notes and the --kda-fp8 option text describe BF16 KDA as the two-GPU default, so the documents differ, and the launcher's choice is what runs. VC-fp8-path-context (source reading, source reading)
