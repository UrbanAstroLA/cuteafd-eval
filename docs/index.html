CuteAFD and tpurtell's vLLM fork on two RTX PRO 6000s

Two inference engines by the same author, tpurtell (wrldsuksgo2mars on Hugging Face), on the same model and machine:

  • CuteAFD (tpurtell/cuteafd), his own runtime, built for attention/FFN disaggregation (AFD): attention and the expert (feed-forward) layers run as separate workers, so experts can sit on other machines; here, on two GPUs, they stay local.
  • His vLLM fork (tpurtell/glm-5.3-flash-ext3-2x-rtx), his vLLM-based engine for this model on two RTX GPUs.

The model is GLM-5.3-Flash on two RTX PRO 6000 Blackwell Max-Q GPUs at 300 W, in two quantized checkpoints: K3.25 (tpurtell's mixed 3.25-bit EXL3 experts) and K4 (brandonmusic's 4-bit EXL3 experts, Local Inference Lab). The questions: how close each engine stays to the original BF16 model, how fast it is, and how to set it up.

Results as of 2026-10-28; versions tested: CuteAFD v3.0.1, vLLM fork v0.9.2. Measured by Michael M (UrbanAstroLA).

Findings

  • Precision: the quantization matters more than the engine. On K3.25, KL from the BF16 model (teacher panel) is 0.0458 on the vLLM fork and 0.0476 on CuteAFD. The largest engine difference is on long code (8-16K-token prompts): CuteAFD +0.0054 further on K3.25, +0.0090 on K4 (top-20 measure). Precision
  • Speed: CuteAFD generates faster; under concurrency the vLLM fork's first tokens come sooner. One stream: 114-168 tokens/s on the vLLM fork, 120-235 on CuteAFD (K3.25). First token, one request: 1K prompt 0.25 s and 0.41 s, 128K prompt 35.1 s and 29.6 s. With 4-16 requests at once the vLLM fork's first tokens come sooner in most cells, while tokens per second are level or ahead on CuteAFD except at 1K × 8. Speed
  • A CuteAFD setting trades about 4% first-token time for precision. W8A16 prefill closes about 59% of the long-code difference on K3.25 (8K prose prompt 1.808 → 1.878 s); W8A16 prefill with the amax scale rule closes about two thirds on K4 (32K code prompt 7.38 → 7.69 s), decode level. Settings
  • Long tasks: the same at the longest cap; CuteAFD finished more code at 32K. At the 128K cap code passed every test in 7/8 (K3.25) and 8/8 (K4) on both engines, math 8/8. At the 32K cap CuteAFD finished 4/8 (K3.25) and 5/8 (K4) code tasks, the vLLM fork 0/8 and 0/8, consistent with CuteAFD's shorter code replies (0.74x and 0.77x the vLLM fork's median length at 128K); descriptive, n = 8. Needles in prompts of 256K to 1M tokens (K3.25): all found on both (exploratory); at 1M the first token took 270 s on the vLLM fork and 254 s on CuteAFD. Long tasks
  • Practical. Ready to serve in 382 s on the vLLM fork (JIT caches kept) and 89 s on CuteAFD. A repeated 8K prompt: 2.10 s on the vLLM fork, 0.017 s from CuteAFD's prefix cache. Only CuteAFD honours "thinking off". K4 KV cache: 1,377,179 tokens on the vLLM fork, 447,488 on CuteAFD. Running it

Does the precision difference matter?

KL is how far an engine's next-token probabilities are from the BF16 model's on the same text (0 is identical, lower is closer; units: nats).

  • The quantization's own distance dwarfs the engine difference. On tpurtell's set his official FP8 model scores 0.0216, the 3.25-bit checkpoint 0.0451 (vLLM fork) and 0.0484 (CuteAFD): the engine difference is 7% of the vLLM fork's distance (11% on long code). K4 roughly halves the distance on both.
  • tpurtell's bar counts a paired change below 0.005 KL or 0.5 top-1 points as within it (defined for changes to one engine; applied here by analogy). K3.25 overall is inside on KL (+0.0033, interval to +0.0049), not on top-1 (−0.46 points, to −0.73); long code is not shown inside on either checkpoint (+0.0054, +0.0090); K4 with W8A16 prefill + amax reads +0.0030 (to +0.0049).
  • On tasks, code and math checks at the 128K cap and the needle checks came out the same on both engines.
  • Not measured: the distance from BF16 beyond 14.4K tokens (no reference exists there) and on the decode path (scoring runs prompts through prefill).

# the launcher: tpurtell's vLLM fork repository at tag v0.9.0; its start.sh runs the v0.9.2 image pinned below

export GPU_MEMORY_UTILIZATION=0.95       # the default 0.97 does not start beside a desktop session
export PORT=127.0.0.1:8001               # the default publishes port 8001 on every interface

export DEBUG_ENV="TILELANG_CACHE_DIR=/root/.cache/tilelang

  TORCHINDUCTOR_CACHE_DIR=/root/.cache/torchinductor
  CUDA_CACHE_PATH=/root/.cache/nv/ComputeCache"

How sure are we

  • K3.25: frozen protocol. After the runs, a separate reviewer who did not run the measurements re-ran the scorers and checked the claims against the receipts; its corrections are applied (Review). It covered the precision and speed blocks and the vLLM fork's long output; it did not cover CuteAFD's long output, the follow-ups F1-F3 (it saw their designs and the F1 baseline speed run), the drift repeats, the startup measurement or the needle pilot. CuteAFD is paired with three vLLM runs from two launches. Thin: 8 long replies per content type, six long documents. K3.25 speed noise: a repeat hours later moved the median by under 2% and single cells by up to 13%; single-cell ratios within ±10% read as level.
  • K4: frozen protocol; no separate review of any part of it, its settings follow-ups included. CuteAFD is paired with two vLLM launches. K4 speed noise: a ±8% band declared before the run (both engines' drift repeats stayed inside it); single-cell ratios within ±8% read as level.
  • One machine: two RTX PRO 6000 Blackwell Max-Q cards at 300 W, with a desktop session using about 2 GB on GPU 1; speed on other power limits or cards was not measured.

Terms

AFD
attention/FFN disaggregation: attention and the expert layers run as separate workers.
BF16 model
the original, unquantized model; the precision reference.
K3.25, K4
the two quantized checkpoints (3.25-bit and 4-bit EXL3 experts).
FP8
8-bit floating point, CuteAFD's format for the other weights.
KL
distance between next-token distributions, in nats; 0 is identical.
Coarse KL, KL20, KL_pb20, KL20n
KL over the reference's top 1,024 tokens plus the rest (tpurtell's rule); over each engine's top 20 (K4, teacher panel); the top-20 form of tpurtell's rule (K4, fidelity set); top 20 shared by two engines (K4, long texts).
Top-1
how often the most likely next token matches the reference's.
P-A, P-B, Q2
the text sets: BF16 teacher texts (2K tokens), tpurtell's fidelity set (to 14.4K), six long documents.
Long code (8-16K)
P-B's longest prompts, all code reading.
95% interval, resolved
a difference's likely range; resolved if it excludes zero.
Level
a speed ratio inside the noise band: not a difference.
Prefill, decode
reading the prompt; generating tokens.
First token
time until the first generated token.
Stream
one request in flight.
W8A8, W8A16
CuteAFD prefill with 8-bit or 16-bit activations.
Scale rule
how CuteAFD makes FP8 scales from BF16 weights at load: pow2 (powers of two, the default), amax (from the largest value), best (the launcher's third rule).
KDA, head
linear-attention projections; the final vocabulary layer.
Drafter
DFlash2, a small model that proposes tokens for the main model to check (speculative decoding).
Serving, scoring launch
the engine as users run it; the same engine with the endpoints that return per-position probabilities for precision scoring.
Block Q, T, L
the measurement blocks: precision, speed (throughput), long output.
Run labels
K3.25: V1 and V1r (vLLM fork, one launch), V2 (a second launch), C1 (CuteAFD), C0 (CuteAFD control on K3.25-v1); K4: V-r1 and V-r2 (two vLLM launches), C-r1 (CuteAFD).
Prefix cache
reuse of a repeated prompt's processed state.
JIT caches
kernels compiled at startup, kept between starts.
Thinking
the model's reasoning before its answer; always on here.
