CuteAFD and tpurtell's vLLM fork on two RTX PRO 6000s

On two RTX PRO 6000s, CuteAFD is the faster engine and tpurtell's vLLM fork is the slightly more precise one; one CuteAFD setting (W8A16 prefill) halves the precision difference for about 4% slower first token. On a second checkpoint, K4, both engines sit roughly half as far from BF16, and the engine pattern holds.

Both engines are tpurtell's. Same model (GLM-5.3-Flash with his 3.25-bit EXL3 experts), same machine, measured under a frozen protocol with an independent audit. Every number comes from the receipts in the repository.

  • If closeness to the BF16 model on long code reading matters most (prompts of 8-16K tokens of source code): the data shows the vLLM fork is closer on both checkpoints: CuteAFD as shipped is +0.0054 KL further at 8-16K on K3.25 and +0.0090 KL_pb20 further on K4 (a top-20 measure, not the same scale). Below 8K on K3.25 no difference is resolved. Evidence: K3.25, K4
  • If you run CuteAFD on K3.25 and want that difference smaller: the data shows W8A16 prefill (GLM5_FLASH_FP8_PREFILL=off) takes the 8-16K difference from +0.0054 to +0.0022 for about 4% longer time to first token and level decode (0.99x); all three FP8 switches leave no resolved difference (+0.0016) at about 4% slower median decode. Follow-up F1, outside the frozen protocol. Evidence: settings map
  • If you run CuteAFD on K4 on two RTX PRO 6000s: the data shows W8A16 prefill with the amax scale rule (GLM5_FLASH_FP8_PREFILL=off, FP8_SCALES=amax) closes about two thirds of the 8-16K difference (+0.0090 → +0.0030 KL_pb20) for about 4% longer time to first token, with decode level. The BF16 KDA and BF16 head options close less on their own and do not fit a serving launch there. Follow-ups K4b-K4d, outside the frozen protocol. Evidence: settings map
  • If you serve one request at a time (a single user, agent loops): the data shows CuteAFD's per-stream decode is 1.02-1.41x the vLLM fork's on K3.25 (cells within about ±10% are run-to-run noise) and 1.05-1.38x on K4 (faster in 10 of 12 one-stream cells, level in 2). Evidence: K3.25, K4
  • If prompts are long (8K-128K tokens) and arrive one at a time: the data shows CuteAFD's first token comes sooner (0.83-0.86x the vLLM fork's time on K3.25, 0.81-0.84x on K4): its prefill runs at about 4,400-4,500 against 3,700-3,900 tokens per second, and at 32K-128K it completes 6-17% more tokens per second end to end (K3.25). With many long prompts at once its first tokens come later (32K input, 16 streams: 106 vs 72 s), because it schedules prefills ahead of decode. Evidence: first token, throughput
  • If prompts are short (about 1K tokens) and many arrive at once: the data shows the vLLM fork answers sooner (0.25 vs 0.41 s to first token at one stream on K3.25) and at 8 streams completes 7-15% more tokens per second. Evidence: first token, throughput
  • If prompts repeat (a long shared prefix): the data shows CuteAFD restored a repeated 8K prompt from its prefix cache in 0.017 s; the vLLM fork reuses only whole 4,352-token blocks and none below about 13K tokens. Evidence: observations
  • If replies are long (up to 128K tokens): the data shows both engines did the same on code and math at the 128K cap on K3.25: code passed every hidden test in 7 of 8 replies (vLLM fork) and 7 of 8 (CuteAFD), math 8/8 and 8/8. On K4 at the 130,048 cap: code 8/8 and 8/8, math 8/8 and 8/8. Descriptive: 8 replies per content type. Evidence: K3.25, K4
  • If you switch models often: the data shows startup to ready takes CuteAFD about 1.5 min, the vLLM fork about 6.4 min with its JIT caches persisted (11.6 min without). Evidence: startup
  • If you need thinking off: the data shows only CuteAFD honours it (one-request check). Evidence: observations
  • If GPU memory is the limit (two RTX PRO 6000s): the data shows both engines serve K3.25 and K4; CuteAFD needs MAX_CONTEXT_TOKENS=262144 to serve K4 there, and its BF16 KDA and BF16 head options do not fit a K4 serving launch. Evidence: K4 observations, K4 settings
  • If you can choose between the two checkpoints: the data shows under the same top-20 measure K4 sits roughly half as far from the BF16 teacher as K3.25 on both engines (P-A KL20: vLLM fork 0.0365 → 0.0192, CuteAFD 0.0380 → 0.0219). Evidence: K4 against K3.25

How sure are we

Solid

  • The precision difference is paired against three vLLM runs from two launches, and survives a leave-one-window-out check and a multiple-comparison correction (independent audit).
  • CuteAFD is bit-deterministic: every repeat was byte-identical.
  • Speed did not drift: repeats hours later were within ±2% at the median on both engines.
  • Both engines ran every request with 0 errors.

Thin

  • Long output: two seeds per prompt, four prompts per content type.
  • Long-document NLL (32K-128K): six documents.
  • The BF16 reference stops at 14.4K tokens; beyond it the engines are compared only with each other.
  • Precision was scored in prefill shape; the decode path that generates tokens was not scored.
  • Single speed cells vary by up to ±13% between runs.

Terms

KL (Kullback-Leibler divergence)
How far an engine's next-token probabilities are from the original BF16 model. 0 means identical; lower is better. Measured in nats. tpurtell's fidelity set treats a paired change below 0.005 as within its bar.
Top-1
How often the engine's most likely next token is the reference's most likely one.
History
The number of tokens before a scored position: what the model had read when it made that prediction. Each headline KL states the range (minimum, median, maximum) of its scored positions.
Tail (p99, p99.9)
The per-position KL that 1% (0.1%) of scored positions exceed. A mean can hide a few positions where the distributions differ a lot; the tail shows them.
NLL
Negative log-likelihood of the actual text: lower means the engine found the text less surprising.
TTFT
Time to first token: from sending a request to the first generated token; mostly prompt processing.
Prefill
Processing the prompt before generation starts. Decode: generating tokens one step at a time.
Stream
One request in flight. Aggregate: all completion tokens of a batch divided by its wall time.
W8A8 / W8A16
FP8 weights with FP8 or 16-bit activations in CuteAFD's prefill matrix multiplies.
