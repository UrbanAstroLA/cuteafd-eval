Investigation: does the 6-bit core make K4-Core-K6 think longer?

On code, K4-Core-K6's 6-bit core and the original BF16 core give the same thinking length on the vLLM fork (1.00x [0.96, 1.04] on 12 code prompts written for the test). On CuteAFD v4.0.0 the same comparison reads 1.26x [1.24, 1.29], above 1 on all 12 prompts, and the two engines differ (0.79 [0.75, 0.83]). Set side by side, three of the four configurations think about as long; the one that differs is CuteAFD's BF16-core configuration, which runs the core, the KDA projections, the vocabulary head and prefill activations in FP8 (the launcher's defaults for a BF16 core): 0.79-0.82x the other three on the 12 new prompts (0.78x over all 16), shorter on every prompt, with tests passing as often as the native 6-bit core. Switching that configuration's FP8 launch settings off cumulatively places the difference in the KDA setting: with the KDA projections in BF16 (on this two-GPU layout that also turns off KDA output sharding, which v4 runs only with FP8 KDA) it thinks 1.31x [1.24, 1.38] longer and is not distinguishable from the native 6-bit core (native core / BF16-KDA arm 0.96x [0.92, 1.01], interval includes 1); the FP8 vocabulary head and FP8 prefill activations show no step. The routed experts contribute nothing measurable (0.99x [0.93, 1.05]). On GPQA reasoning neither part changes thinking length or when the model decides to stop, now on 41 questions on both engines; a swap of the q_b and output projections that shifted the stop decision on the first 11 questions does not on 30 new ones. Whether the core changes how often replies loop is open.

Direction, everywhere on this page except the vLLM per-group table: ratios put K4-Core-K6, or the part of it under test, first (in the FP8 section, steps put the arm with the setting switched off first; each ratio names its arms) (above 1 = it thought longer); differences are K4-Core-K6's side minus the other (below 0 = it was less ready to stop). G4's published reading is stated the other way (BF16 / 6-bit = 0.80); here it is 1.25. Every claim on this page, with its status, value and a pointer into the file it comes from, is in findings.json.

How the results fit together

  • No length difference from the 6-bit weights is detected; the difference goes with CuteAFD's KDA setting. On the vLLM fork, where the 6-bit core is rebuilt to BF16 at load and both arms run as BF16 matrices, the code study reads 1.00x [0.96, 1.04]. On CuteAFD the same prompts and seeds read 1.26x [1.24, 1.29], and the engines differ (0.79 [0.75, 0.83]), which by the rule stated before the run places the CuteAFD gap in how CuteAFD serves the core, not in the weight values. Post hoc, the arm that stands apart is CuteAFD's BF16 core converted to FP8 at load (50.4K median reasoning tokens, about 0.82x the vLLM BF16 core on the 12 new prompts, shorter on all 16); CuteAFD's native 6-bit core sits with both vLLM arms (1.04x the vLLM BF16 core). So this page's earlier “the 6-bit core thinks longer on code” is better read as “the FP8-from-BF16 core thinks shorter”. That arm differs in more than the core's rounding: by the launcher's defaults, with a BF16 core it also puts the 34 KDA layers' projections (including three gate projections that are BF16 in both checkpoints) and the vocabulary head in FP8, and prefill runs the MLA and MLP projections with FP8 activations; with the native 6-bit core these stay on the 6-bit kernels or in BF16 (CUTEAFD-FP8-PATH.md). The engine's author states the reasons (decode speed and pool size; output sharding to avoid rounding the two GPUs' partial outputs) and checks them on teacher-forced top-1 and KL (launcher comment, model notes, --kda-fp8 option text; the model notes and option text describe BF16 KDA as the two-GPU default, so the documents differ). This study measures free generation of long reasoning with speculative decoding. K4 is served the FP8 way as well. Switching the three settings off cumulatively puts the whole difference in the KDA setting, which switches the KDA projections to BF16 and, on this two-GPU layout, KDA output sharding off (1.31x [1.24, 1.38]; head and prefill no step; section below).
  • The shorter reasoning is not shown to cost correctness. On CuteAFD hidden tests pass on 50 and 49 of 64 replies (the arms agree on all-pass in 51 of 64 pairs); on the vLLM fork 53 and 58. The FP8-from-BF16 core reaches the same results as the native core with about a fifth less reasoning on these prompts. Post hoc, the arms with CuteAFD's FP8 settings switched off and the vLLM BF16 core pass all tests more often than both CuteAFD code-study arms (vLLM BF16 core against the FP8-from-BF16 core +14 points [+3, +26]); after allowing for 13 looks only the arm with all three settings off still differs. The native core, which has none of those settings, passes about as often as the FP8-from-BF16 core, so this is not read as “FP8 costs passes” (FP8 section).
  • The routed experts are ruled out at this resolution. 0.99x [0.93, 1.05]; the total is the core times the experts (1.16 × 0.99 ≈ 1.15).
  • It is tied to code, not to reasoning in general. On GPQA reasoning no length difference shows (Block L reasoning 1.05x [0.85, 1.39]; vLLM G4, finished replies, 1.03x), and the stop decision on fixed GPQA traces does not move for the core on either engine, now on 41 questions. On code, only CuteAFD's FP8-from-BF16 core differs. How the stop decision behaves on code text has not been scored.
  • The difference does not build up along the reply on the GPQA traces: on both engines the top-64 KL between the core arms is highest in the first 1,024 tokens (CuteAFD 0.0162), flat from 1K to 64K (0.0110-0.0120) and lower beyond. Whether the same holds on code text is unmeasured.
  • q_b and the output projections. The two groups that met G2's rule, swapped to BF16 together with the KDA output projection, shift the stop decision on the 11 questions they were found on (6-bit side −0.012 [−0.020, −0.005], launch noise 0.0018), not on 30 new questions (+0.003 [−0.006, +0.016]). The whole core in BF16 shows no such shift on either set. The flags are specific to those 11 questions.
  • The two engines' “BF16 core” differ. The vLLM loader serves it as BF16; CuteAFD converts it to FP8 at load, which is how it serves K4. That difference is now where the code result sits (first point), and within it the KDA setting. K4's core is served the same way on CuteAFD, so the earlier Block L reading (K4-Core-K6 thinking longer than K4 on code) carries the same FP8-from-BF16 arm.
  • The core is also what makes K4-Core-K6 slower on CuteAFD: with its BF16 core converted to FP8, its experts decode at K4's speed (130 against 129 tok/s on code); with the native 6-bit core, 121.

  • These are the launcher's defaults, with the author's stated reasons. The launcher comment, model notes, --kda-fp8 option text give them: row128 KDA (FP8 with one scale per row and 128 input columns) and an FP8 head for decode speed and pool size, checked on 512 teacher-forced positions (top-1, KL); on the two-GPU split, KDA output sharding, added because it avoids rounding the two GPUs' half-width BF16 partial outputs. The model notes state that the speculation check does not establish byte-identical speculative output; the option text, that row128 doubles the rounding difference between verify steps (several drafted tokens checked at once) and single-token decode. The model notes and option text describe BF16 KDA as the default on the two-GPU split; the launcher comment and every launch here use row128 (the v3.0.1 audit, U2 noted the same difference). This run measures free generation of long reasoning with the drafter (the speculative-decoding draft model) on.
  • Where in the engine (judgement from source and measurements, not isolated by its own run). Most likely on the generation path (decode and speculative verify); prefill is not excluded. Prompts are 1,155-1,758 tokens against medians of 50-68K reasoning tokens. Speculative verify steps run on the decode programs, which read the FP8 KDA copies, and KDA output sharding is not limited to prefill (engine.rs:4660, :3844-3847, :4666-4695). Not excluded: the setting also changes the KDA projections in prefill, and the recurrent state the prompt leaves seeds every later token. The prefill-activation switch covers the MLA and MLP activations, not the KDA projections, so it does not bear on this. The teacher-forced results on this page (stop decision, KL) run through the prefill programs on GPQA traces and do not measure this path on code. Not separated: KDA in prefill against generation, and plain decode against speculative verify, which take different KDA kernels with FP8 KDA.
  • What the KDA setting covers. One FP8 operand (E4M3, one scale per row and 128 input columns, power-of-two scales) packs q, k, v and the f_a, g_a and b projections of the 34 KDA layers (the last three are BF16 in both checkpoints); the KDA output projection is its own FP8 operand in the same setting. The launcher's automatic setting selects it for a checkpoint without a native KDA format, including K4 (CUTEAFD-FP8-PATH.md). On a two-GPU head split the automatic setting also adds token-row KDA output ownership (--kda-output-shard --kda-prefill-expanded), which v4 accepts only with FP8 KDA; with KDA in BF16 the layers reduce the two GPUs' partial outputs instead (tpurtell/cuteafd v4.0.0: run-family.sh:2366, mod.rs:1296-1299). The native 6-bit core runs without that sharding too (mod.rs:1716-1722). So the F-kda step changes the KDA weights' format and the KDA split path together; which of the two goes with the length is not separated. The independent review of the v3.0.1 comparison raised the same point for its precision follow-up (v3.0.1 audit, U2).
  • MLA projections, including MLA q_b and o_proj. They stay FP8 in every F arm, while the native core runs them as 6-bit, and the gap still closes at F-kda (native / F-kda 0.96x [0.92, 1.01]): on code length, FP8 MLA projections show no measurable shortening at this resolution. Their effect on the stop decision was tested on the vLLM fork (G2 and its follow-up), where the swapped group also included the KDA output projections, which on CuteAFD belong to the KDA setting.

One measure differs between the engines: the mean log p(</think>) over the 512 tokens before the close, where p is about 10⁻⁶. BF16 side minus 6-bit, it reads +0.057 [+0.011, +0.104] on CuteAFD and −0.115 [−0.148, −0.092] on the vLLM fork, and again on the 30 new questions (+0.106 [+0.064, +0.148] and −0.114 [−0.132, −0.096]). It measures the far tail of the head's distribution, where FP8 and BF16 serving differ. In linear terms over the same tokens (hazard, figure above) the engines agree in sign on the new questions.

What was tested

  • CuteAFD (the engine where the question arose). tpurtell's CuteAFD v4.0.0, unmodified. Three arms (table above) separate the core from the routed experts; the derived checkpoint is a local build, not a producer release. Step 2, the fixed traces, ran first (four scoring launches, including a second K4-Core-K6 launch); step 1, free generation, followed. Protocol frozen before the first request: PROTOCOL.md. The Block L ratio that raised the question and the max-p check are post hoc.
  • vLLM fork, arms. One checkpoint, wrldsuksgo2mars/GLM-5.3-Flash-EXL3-K4-Core-K6 (K4 routed experts, 6-bit EXL3 core and head). The 6-bit arm rebuilds its 316 core tensors to BF16 at load (exact arithmetic, one rounding). Each swap arm loads the named group's original tensors from zai-org/GLM-5.3-Flash-BF16 @ f9fed3bb, the checkpoint's own source, instead; every launch logged the expected number of swapped tensors. Same engine, image, loader and kernels on every arm.
  • vLLM fork, engine. tpurtell's vLLM fork v0.9.2 release image with a local loader modification (not a tpurtell release; the release does not load this checkpoint): repro/vllm-k6-loader.
  • G2, fixed traces. 77 finished and 16 unfinished reasoning traces, each teacher-forced through every arm: 52 from earlier hard-question probes (questions 13, 79, 88, 121, 127; K3.25 and K4 on earlier fork versions, so off-policy here) and 41 generated by the 6-bit arm itself on the seven length-variable questions. Open questions

  • What inside the KDA setting? Measured: the setting carries the difference (section above). Not separated: the KDA projections' FP8 format against the KDA split path that comes with it on two GPUs (output sharding), the power-of-two scale rule, which projections (q, k, v, the f_a, g_a and b gate projections, or the KDA output projection) matter, and where it acts: KDA in prefill, plain decode or the speculative verify step (judged most likely the generation path).
  • Does precision change how often code passes its tests? Post hoc direction only: the arms with CuteAFD's FP8 settings off and the vLLM BF16 core pass more often than both code-study arms; 5 of 13 paired intervals exclude 0, 2 after allowing for 13 looks (all three settings off, against each code-study arm). The native core passes about as often as the FP8-from-BF16 core, and passing does not follow length.
  • Where does the small overshoot come from? Post hoc: with the head (and then prefill) also off, the BF16 core thinks about 6% longer than the native core on the 12 new prompts (not on all 16). Not located: the head step, chance, the FP8 MLA and MLP projections (no BF16 option), the core's format, or another difference.
  • Does the core change the stop decision on code text? Unmeasured: every fixed trace scored so far is GPQA reasoning.
  • Does it hold beyond these 16 Python projects? One prompt family, one checkpoint; prose moved less (1.04x on 4 prompts).
  • Does the 6-bit core change how often replies loop? Measured: 1 loop in 18 samples of question 12 on the 6-bit core (6 earlier, 12 in G4), 0 in 12 on the BF16 core (Fisher p = 1.0), vLLM fork; on the seven questions, K4-Core-K6 reached the cap about as often as K4 and K3.25 in earlier records (table above). No CuteAFD reply reached the cap (224 replies, code and prose).

Caveats

  • Two engines, one machine. The vLLM loader rounds the 6-bit core once from exact arithmetic; CuteAFD runs it natively and the producer's own rebuild rounds at FP16 between stages (15.8% of elements differ, 2.4% by more than one BF16 unit). CuteAFD's “BF16 core” is BF16 converted to FP8 at load; the vLLM fork's is BF16. The cross-engine comparison of absolute lengths is post hoc and averages within each prompt before averaging prompts, since seeds do not reproduce samples across engines.
  • The routed experts are compared as two whole quantizations (K4-Core-K6's and K4's), not tensor by tensor; the derived checkpoint is a local build, not a producer release.
  • Free generation on CuteAFD covers 8 prompts (4 code, 4 prose), 4 replies per prompt per arm; the Block L ratio that raised the question is post hoc. G4 on the vLLM fork is one GPQA question; the knife-edge questions where replies tip between short and capped were dropped from G4 because their spread would need hundreds of samples per arm.
  • The code study's 12 new prompts were written for it (specs, reference implementations and tests published); p0-p3 raised the question and are reported separately. One prompt family (Python packages), 4 seeds per prompt.
  • The FP8 ablation is cumulative: each step is measured with the earlier settings already off, so interactions between them are not separated. Its arms ran a day after the code study's arms on the same engine and config (a replayed request was identical).
  • The fixed traces are GPQA reasoning generated on the vLLM fork, teacher-forced on both engines. The new questions are a random draw and mostly easy for this model; on many of their traces p(</think>) at the close is near 1 on every arm.
  • KL here is a top-64 measure with the arm's 64th value as the floor for tokens outside its top 64 (a lower bound), not full vocabulary. GLM tokenizer throughout; not comparable with other model families.
