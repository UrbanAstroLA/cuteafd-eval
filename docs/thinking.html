Investigation: does the 6-bit core make K4-Core-K6 think longer?

On CuteAFD v4.0.0, K4-Core-K6's native 6-bit core makes its code replies think longer. On 12 code prompts written for the test, it thought 1.26x [1.24, 1.29] as long as the same checkpoint with its BF16 core (converted to FP8 at load), above 1 on all 12 prompts, with the tests passing as often (50 and 49 of 64 replies). The routed experts contribute nothing measurable (0.99x [0.93, 1.05]). The earlier, smaller runs pointed the same way (code 1.43x read after the fact; 1.16x [0.98, 1.36] on 8 prompts, inconclusive). On GPQA reasoning neither part changes thinking length or when the model decides to stop, now on 41 questions on both engines; a swap of the q_b and output projections that shifted the stop decision on the first 11 questions does not on 30 new ones. Whether the code effect comes from the 6-bit weights or from how CuteAFD serves them is being measured on the vLLM fork with the same prompts and seeds. Whether the core changes how often replies loop is open.

Direction, everywhere on this page except the vLLM per-group table: ratios put K4-Core-K6, or the part of it under test, first (above 1 = it thought longer); differences are K4-Core-K6's side minus the other (below 0 = it was less ready to stop). G4's published reading is stated the other way (BF16 / 6-bit = 0.80); here it is 1.25.

How the results fit together

  • The 6-bit core makes code replies think longer on CuteAFD. The first reading (code 1.43x, read after the fact) shrank on 8 prompts with new seeds (1.25x on code, interval over 8 prompts including 1). The code study then used 16 code prompts, 12 of them new, 4 seeds each: 1.26x [1.24, 1.29] on the new prompts, every prompt above 1, the 6-bit core longer in 58 of 64 seed pairs. This revises the earlier “inconclusive”: that interval was wide because of the prompt count, not because the effect was absent.
  • The extra thinking does not change the outcome. Hidden tests pass on 50 and 49 of 64 replies; the two arms agree on all-pass in 51 of 64 pairs. Median reasoning 63.7K against 50.4K tokens, at 115 against 122 tok/s: on these prompts the 6-bit core costs about a third more time per code reply for the same result.
  • The routed experts are ruled out at this resolution. 0.99x [0.93, 1.05]; the total is the core times the experts (1.16 × 0.99 ≈ 1.15).
  • It is tied to code, not to reasoning in general. On GPQA reasoning no length difference shows (Block L reasoning 1.05x [0.85, 1.39]; vLLM G4, finished replies, 1.03x), and the stop decision on fixed GPQA traces does not move for the core on either engine, now on 41 questions. How the stop decision behaves on code text has not been scored.
  • The difference does not build up along the reply on the GPQA traces: on both engines the top-64 KL between the core arms is highest in the first 1,024 tokens (CuteAFD 0.0162), flat from 1K to 64K (0.0110-0.0120) and lower beyond. Whether the same holds on code text is unmeasured.
  • q_b and the output projections. The two groups that met G2's rule, swapped to BF16 together with the KDA output projection, shift the stop decision on the 11 questions they were found on (6-bit side −0.012 [−0.020, −0.005], launch noise 0.0018), not on 30 new questions (+0.003 [−0.006, +0.016]). The whole core in BF16 shows no such shift on either set. The flags are specific to those 11 questions.
  • The two engines' “BF16 core” differ. The vLLM loader serves it as BF16; CuteAFD converts it to FP8 at load, which is how it serves K4. The CuteAFD core contrast is 6-bit against FP8-from-BF16, on CuteAFD's kernels; the same 16 code prompts and seeds on the vLLM fork, where the 6-bit core is rebuilt to BF16 at load and runs on the same kernels as the BF16 core, are being run to separate the weights from the serving path.
  • The core is also what makes K4-Core-K6 slower on CuteAFD: with its BF16 core converted to FP8, its experts decode at K4's speed (130 against 129 tok/s on code); with the native 6-bit core, 121.

What was tested

  • CuteAFD (the engine where the question arose). tpurtell's CuteAFD v4.0.0, unmodified. Three arms (table above) separate the core from the routed experts; the derived checkpoint is a local build, not a producer release. Step 2, the fixed traces, ran first (four scoring launches, including a second K4-Core-K6 launch); step 1, free generation, followed. Protocol frozen before the first request: PROTOCOL.md. The Block L ratio that raised the question and the max-p check are post hoc.
  • vLLM fork, arms. One checkpoint, wrldsuksgo2mars/GLM-5.3-Flash-EXL3-K4-Core-K6 (K4 routed experts, 6-bit EXL3 core and head). The 6-bit arm rebuilds its 316 core tensors to BF16 at load (exact arithmetic, one rounding). Each swap arm loads the named group's original tensors from zai-org/GLM-5.3-Flash-BF16 @ f9fed3bb, the checkpoint's own source, instead; every launch logged the expected number of swapped tensors. Same engine, image, loader and kernels on every arm.
  • vLLM fork, engine. tpurtell's vLLM fork v0.9.2 release image with a local loader modification (not a tpurtell release; the release does not load this checkpoint): repro/vllm-k6-loader.
  • G2, fixed traces. 77 finished and 16 unfinished reasoning traces, each teacher-forced through every arm: 52 from earlier hard-question probes (questions 13, 79, 88, 121, 127; K3.25 and K4 on earlier fork versions, so off-policy here) and 41 generated by the 6-bit arm itself on the seven length-variable questions. Top-64 log-probabilities at sampled rows and at the last 512 rows before each close, plus the exact log-probability of </think> at every stored row. Plus the P-A teacher panel (25 × 2,048 tokens). CuteAFD scored the same traces at the same rows.
  • vLLM protocols. G2's reading rule was frozen before the first capture; a second launch of the 6-bit arm was added (Amendment 1) before any capture was read, because the fork's long-prompt prefill varies between launches. G4 was frozen after G2 was read and before its first sample. The loop checks were chosen after G4 was read and are exploratory.
  • Code study (CuteAFD). The core-swap arms C-K6 and C-K6x on 16 code prompts × 4 seeds, the same seed on both arms, the v4 Block L driver unchanged; 12 of the prompts written for it, before any request. Primary set and rule frozen before the first request: PROTOCOL.md.
  • Position (no new requests). The existing dumps of both engines, by position along the trace; criteria written before computing: NOTE.md. CuteAFD v4.0.0 loads its native core only whole (every layer's attention and FFN groups native together), so the single-group swaps exist on the vLLM fork only; a CuteAFD attention-only arm was refused at load.
  • q_b and output projections together (vLLM fork). 56 tensors, launches interleaved K4-Core-K6, swap, K4-Core-K6, swap; frozen before the first launch: FROZEN-QBO.json.
  • New questions. 30 GPQA Diamond questions drawn at random (seed 20261106) from those not used before; K4-Core-K6 on the vLLM fork wrote 3 replies each (all 90 finished, 87 correct, median 2.4K tokens: mostly easier than the first 11, which were chosen as loop-prone or length-variable); every vLLM arm and both CuteAFD core arms scored the finished replies. Frozen before the first launch: PROTOCOL.md.

  • Does the code effect go with the 6-bit weights or with CuteAFD's serving of them? Measured on CuteAFD only, where the comparison arm is FP8-from-BF16 on different kernels. The vLLM fork run on the same prompts and seeds is in progress.
  • Does the core change the stop decision on code text? Unmeasured: every fixed trace scored so far is GPQA reasoning.
  • Does it hold beyond these 16 Python projects? One prompt family, one checkpoint; prose moved less (1.04x on 4 prompts).
  • Does the 6-bit core change how often replies loop? Measured: 1 loop in 18 samples of question 12 on the 6-bit core (6 earlier, 12 in G4), 0 in 12 on the BF16 core (Fisher p = 1.0), vLLM fork; on the seven questions, K4-Core-K6 reached the cap about as often as K4 and K3.25 in earlier records (table above). No CuteAFD reply reached the cap (224 replies, code and prose).

Caveats

  • Two engines, one machine. The vLLM loader rounds the 6-bit core once from exact arithmetic; CuteAFD runs it natively and the producer's own rebuild rounds at FP16 between stages (15.8% of elements differ, 2.4% by more than one BF16 unit). CuteAFD's “BF16 core” is BF16 converted to FP8 at load.
  • The routed experts are compared as two whole quantizations (K4-Core-K6's and K4's), not tensor by tensor; the derived checkpoint is a local build, not a producer release.
  • Free generation on CuteAFD covers 8 prompts (4 code, 4 prose), 4 replies per prompt per arm; the Block L ratio that raised the question is post hoc. G4 on the vLLM fork is one GPQA question; the knife-edge questions where replies tip between short and capped were dropped from G4 because their spread would need hundreds of samples per arm.
  • The code study's 12 new prompts were written for it (specs, reference implementations and tests published); p0-p3 raised the question and are reported separately. One prompt family (Python packages), 4 seeds per prompt.
  • The fixed traces are GPQA reasoning generated on the vLLM fork, teacher-forced on both engines. The new questions are a random draw and mostly easy for this model; on many of their traces p(</think>) at the close is near 1 on every arm.
  • KL here is a top-64 measure with the arm's 64th value as the floor for tokens outside its top 64 (a lower bound), not full vocabulary. GLM tokenizer throughout; not comparable with other model families.
