Method

How the comparison was set up and measured.

Each engine ran as its author ships it, with a short list of local changes, on one machine. Precision was scored teacher-forced against a BF16 reference; speed and long output with one client, unique prompts and a distinct seed per request. The protocol was frozen before the speed and long-output runs; three follow-ups and a drift check were declared later and are labelled as such.

Principles (why this is not a cherry-picked benchmark)

  1. Grid, prompts, metrics and analysis fixed before any run. Prompts drawn from public sources by a fixed rule and seed; the few authored prompts (JSON, long code specs) are written and hashed here first.
  2. Every cell reported: losses, errors, timeouts, cells an engine cannot run, and cells skipped for cost (listed below with the reason, before any run).
  3. Same inputs, same scorer: identical token ids at identical positions, one scoring program per panel, one client for serving metrics.
  4. Each engine as its author ships it, plus only the documented local deltas (listen address, request logging off, output limit raised, infiniband guard). Settings a measurement path requires (bench endpoint, API key, full-prefill logits) are listed per block.
  5. Distinct recorded seed per request; analysis unit is the prompt or window, paired across engines.
  6. Drift control: engine order C, V, then a predeclared subset of C again (CVC).
  7. Intervals with every number; noise floors measured, not assumed.

F2 — vLLM v0.9.2 prefix cache: why 0 cached tokens on a repeated 8K prompt

Observation (Block T cached cell): the same 8,192-token prompt sent 4 times in sequence got cached_tokens 0 and TTFT 2.10 s each time, with --enable-prefix-caching --mamba-cache-mode align. Design, on the normal served v0.9.2 container (no plugin), one stream, thinking on, max_tokens 16:

  • identical prompts at 1K, 4,352, 8,192, 8,704 and 17,408 tokens (multiples of 4,352 included because of the align mode's block size, per discovery), each sent 3 times in sequence;
  • record usage cached_tokens, TTFT, and /metrics prefix-cache query/hit counters before and after;
  • grep the server log for cache-mode and block-size lines. Cost: a few minutes during the final vLLM session. Reported as: hits or no hits per length, and the evidence for the mechanism if it is visible; no fix attempted.

What each engine returns. vLLM: the target model's own log-probs of the prompt rows (raw logits, no sampling parameters), top 20 plus the forced token; prompt-logprob requests skip prefix-cache reads; speculative decoding does not change them. Both are prefill-shaped: the measure covers prompt arithmetic, not decode-shaped rows.

Metrics. Names are kept distinct from full-vocabulary KL.

  • P-A: KL20, KL(teacher ‖ engine) on the engine's 20 ids plus the actual token plus one rest cell, a lower bound; KL20n, the same on the ids both carry. Exact under top-20: NLL, top-1, confident top-1, top-3.
  • P-B: KL_pb20, the top-20 truncation of tpurtell's top-1,024-plus-tail rule; exact: top-1, confident top-1, top-3, NLL. Groups: generated rows (primary), by bucket, by block (8-16K is block B, long code reading), block A by bucket; context rows separately (hypersensitive filler).
  • Q2: NLL; engine against engine KL20n both directions and top-1 agreement; floors from repeats.

Calibration (zero-GPU check before the freeze, on the K3.25 run's full-vocabulary captures truncated to each engine's own top 20): on P-A, KL20 read 0.79-0.80 of the full-vocabulary KL on every arm; on P-B generated rows, KL_pb20 kept 98-99% of the published coarse KL. Every K3.25 difference whose interval excluded 0 kept its sign and its significance under the truncation. The K4 scorers reproduce those per-row values exactly when fed emulated top-20 rows. Reading rule (declared before any request). "C differs from vLLM" on a measure needs both: the 95% interval of C − Vmean excludes 0, and |C − Vmean| exceeds the vLLM launch-to-launch difference |V-r2 − V-r1| on the same rows. Otherwise it reads "within vLLM's own launch-to-launch spread". The primary looks are P-A KL20, P-B generated KL_pb20 and P-B generated top-1. Block T: throughput

  • Inputs: the K3.25 Block T prompt set, unchanged. Prose and code at every length; reasoning and JSON at 1K and 8K.
  • 3 replicates per cell, 1,024 output tokens, thinking on; at c streams a replicate is lcm(c, 4)/c barrier-released batches, so every prompt appears equally often. One warm-up batch and one cached cell (8K prose prompt 0, a primer and 3 repeats). 272 requests per engine (264 measured, 4 warm-up, 4 cached).
  • Per request: time to first token, prefill rate at one stream, per-stream decode, usage, finish reason, content and reasoning characters. Per replicate: aggregate tokens per second.
  • Analysis: per cell the median decode, the decode of "clean" streams (decode windows overlapping other streams' prefill by less than 5%), the aggregate, the median time to first token, prompt-token mismatches and cached tokens; ratios to vLLM with the range over replicates.
  • Reading rule. The noise band per cell is max(8%, the largest drift deviation of either engine); both engines' drift stayed inside 8%, so the band is 8%. Inside it a ratio is "level"; outside, "faster" or "slower", stated no more precisely than the band. The 128K code cells hold literal <think> / </think> text and are reported with the smoke check's finding.
  • Drift: 1K and 32K, 1 and 4 streams, code and prose, replicates 0-1 (64 requests), seeds +30,000,000 and its own salt; reported as later over earlier per cell.
