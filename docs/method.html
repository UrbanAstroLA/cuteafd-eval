Method

How the comparison was set up and measured.

Each engine ran as its author ships it, with a short list of local changes, on one machine. Precision was scored teacher-forced against a BF16 reference; speed and long output with one client, unique prompts and a distinct seed per request. The protocol was frozen before the speed and long-output runs; three follow-ups and a drift check were declared later and are labelled as such.

Principles (why this is not a cherry-picked benchmark)

  1. Grid, prompts, metrics and analysis fixed before any run. Prompts drawn from public sources by a fixed rule and seed; the few authored prompts (JSON, long code specs) are written and hashed here first.
  2. Every cell reported: losses, errors, timeouts, cells an engine cannot run, and cells skipped for cost (listed below with the reason, before any run).
  3. Same inputs, same scorer: identical token ids at identical positions, one scoring program per panel, one client for serving metrics.
  4. Each engine as its author ships it, plus only the documented local deltas (listen address, request logging off, output limit raised, infiniband guard). Settings a measurement path requires (bench endpoint, API key, full-prefill logits) are listed per block.
  5. Distinct recorded seed per request; analysis unit is the prompt or window, paired across engines.
  6. Drift control: engine order C, V, then a predeclared subset of C again (CVC).
  7. Intervals with every number; noise floors measured, not assumed.

F1 — CuteAFD FP8 ablation on the 8-16K precision gap

Question: which of CuteAFD's FP8 choices account for its P-B gap to vLLM at 8-16K (C1 − V1 KL +0.0044, top-1 −1.04 pts, generated rows)? CuteAFD is bit-deterministic, so single runs per arm suffice.

Reading rule (declared now): an arm "accounts for" the gap at 8-16K if it moves C1's 8-16K KL toward V1 by more than the paired interval of C1 − V1; partial movement is reported as partial. Any arm that fails memory admission is reported as not runnable.

F2 — vLLM v0.9.2 prefix cache: why 0 cached tokens on a repeated 8K prompt

Observation (Block T cached cell): the same 8,192-token prompt sent 4 times in sequence got cached_tokens 0 and TTFT 2.10 s each time, with --enable-prefix-caching --mamba-cache-mode align. Design, on the normal served v0.9.2 container (no plugin), one stream, thinking on, max_tokens 16:

  • identical prompts at 1K, 4,352, 8,192, 8,704 and 17,408 tokens (multiples of 4,352 included because of the align mode's block size, per discovery), each sent 3 times in sequence;
  • record usage cached_tokens, TTFT, and /metrics prefix-cache query/hit counters before and after;
  • grep the server log for cache-mode and block-size lines. Cost: a few minutes during the final vLLM session. Reported as: hits or no hits per length, and the evidence for the mechanism if it is visible; no fix attempted.
