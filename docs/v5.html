CuteAFD v5.0.0: core precision at long context

CuteAFD v5.0.0 adds ATTENTION_MODE, which selects the precision at which two groups of attention projections of the HQA checkpoint of GLM 5.3 Flash run. It has three values; the graded runs here cover two, hqa (BF16 copies) and compact (K6 copies), and the third, fp8-compact, appears only in an exploratory check. A locally derived all-BF16 core (anchor) is the reference here, not a recommendation, and exlr8-k4 is a reference checkpoint in another quantisation format. Updated 2026-11-12 with additions to the frozen two-pass result: four graded passes per configuration, the distance of each configuration from the unquantized BF16 model and, later that day, how the replies ended and the size of each checkpoint in bits per weight.

Size: by bits the four measured configurations are 25.5% to 27.2% of the BF16 model (4.08 to 4.35 bits per weight); a fifth, the K3.25-Core-FP8 checkpoint at 3.55, has its passes running and no measured figures yet. Bits per weight has the table and a short primer on the formats.

Distance from BF16 (two reference sets, contexts to 14.4K): all four sit in one band, KL 0.030 to 0.036 on the fidelity set, between the recorded baseline for the official FP8 model (0.0216) and a K3.25 checkpoint measured on an earlier release of this engine (0.0484); the three probe arms are within 0.003 of each other. Graded tasks, 4K to 127K, four passes: hqa − anchor +0.003 [−0.005, +0.012] and exlr8-k4 − anchor −0.001 [−0.012, +0.009], no difference measured; compact is the lowest in both pass sets, with the gap at 127K (0.887 against 0.918 to 0.924): indicated, not established. Over the four passes the gap is replies to join, one of the three task families, at 127K that did not finish (10 of 80 against 4, 2 and 1), not answers that were wrong, and every configuration shows that ending (How the replies ended). That 127K difference lies beyond the 14.4K reach of both reference sets. Accuracy falls with length in every configuration, anchor included. What each configuration trades puts cost and measured quality side by side.

Bits per weight: one unit for the checkpoints

The configurations on this page mix several storage formats inside one model, and their names (K4, K3.25, Core-K6, FP8) each describe one part. This section puts them on one unit, bits per weight, counted from the checkpoint files, with a short primer for readers who do not work with quantized models. Added later on 2026-11-12.

Weights and bits
a language model is a set of matrices of numbers, its weights. This model's language part has 320.8 billion of them. Bits per weight is the storage a part of the model takes divided by the number of weights in it: how many bits each weight gets on average. It sets the size of the files and, closely, of the model in memory, and a lower value is a coarser copy of the original.
BF16
16 bits per weight, the format the model was released in. It is full precision here, and the 100% mark. At 16 bits the language model would be 597 GiB.
FP8
an 8-bit floating-point number per weight plus a small table of scales: 8.0 to 8.3 bits per weight as stored in these files.
EXL3 and the K numbers
EXL3 is a trellis-coded format: a matrix is stored as a code of K bits per weight plus two short scale vectors. K4 is 4 bits per weight (4.01 as stored) and K6 is 6 (6.01).
Mixed widths
a fractional K is an average over matrices, not a width. In the K3.25 checkpoint three quarters of the expert matrices are stored at 3 bits and one quarter at 4 (27,216 and 9,072 matrices), which comes to 3.26 bits per weight. Which matrix gets which width is the checkpoint author's allocation and is not examined here.
EXLR8
another trellis-coded format, by another author. Its K4 experts are 4.00 bits per weight. The same nominal width in a different design is not the same code, so exlr8-k4 is read as a whole checkpoint.
Where the weights are
94.9% of the weights are the routed experts: 288 small feed-forward blocks in each of 42 layers, of which a token passes through 8 per layer. Everything else in the main layers (attention, shared experts, the dense feed-forward of the first three layers, the output head, the embedding) is 2.8%, and every token passes through all of it. A further 2.3% is a multi-token-prediction block stored after the main layers. So the name on a checkpoint describes its experts and nearly fixes its size, while anchor, hqa and compact differ inside the 2.8% (and, for hqa, in a 0.1 GiB part of the multi-token-prediction block).
Names of the parts
the core is everything in the main layers outside the routed experts. The shared experts are a feed-forward block beside the routed ones that every token passes through. o_proj and q_b_proj are two of the attention projection matrices of a layer, the two that ATTENTION_MODE selects the precision of. The output head turns the last hidden state into token scores. KDA is the engine's name, in its load line (the line it logs when a checkpoint is loaded), for a group of attention matrices it can hold as FP8.
Stored and run
the tables count what the files hold. The engine can hold a matrix in another form in memory; where it does, that is said under the component table. Memory in use is under What each configuration trades.

  • Every configuration here is a 22% to 27% copy of the BF16 model by bits. The four measured ones span 4.08 to 4.35 bits per weight, 0.27 bits end to end, because their experts are all at 4 bits and the experts are 95% of the weights.
  • hqa to compact moves 0.67% of the weights from 16 bits to 6 in the main layers: 4.17 to 4.10 bits per weight, 2.6 GiB of files, 0.1 GiB of it the same two projections in the multi-token-prediction block. anchor to compact moves 2.4% of the weights from 16 bits to about 6 or 7: 4.35 to 4.10, 9.1 GiB. The embedding stays at BF16 in all three.
  • k325-fp8 is the one that changes the experts: 3.26 bits against 4.01 there. Its files are 20.5 GiB smaller than compact's in all: the experts are smaller by more than that, and its core is stored at more bits than hqa's or compact's (as stored; see "As run" above).
  • exlr8-k4 is the smallest of the four measured, though its head and most of its attention projections are FP8, more bits than compact's K6 there. It stores o_proj, q_b_proj, the shared experts and the dense feed-forward in its 4-bit trellis where compact has K6, and its embedding at FP8 where compact's is BF16: 6.55 bits outside the routed experts against 7.25 (the layout figure). Its files are 1.0 GiB smaller in all, 0.3 GiB of that in the experts (4.00 bits against 4.01).
  • Bits per weight is a size, not a quality score. Among the four measured configurations neither distance from BF16 nor task score follows it: hqa at 4.17 is no farther from BF16 than anchor at 4.35 on either set (distance from the BF16 model), and exlr8-k4 at 4.08 scores level with anchor. The unit says what was spent; the sections below say what it bought.

Terms used above.

Probe arms and configurations
the three probe arms are anchor, hqa and compact, which share their K4 experts; the four configurations are those three and exlr8-k4.
Reference
used for three things on this page. anchor is the reference arm of the probe, the all-BF16 core the other arms are read against. exlr8-k4 is a reference checkpoint in another quantisation format. The BF16 model is the unquantized model that distance is measured from. anchor is not the BF16 model: its experts are K4.
Experts
the model's mixture-of-experts feed-forward weights, most of its size; K4 in the three probe arms (anchor, hqa, compact).
Core
the attention and other layer weights outside the experts.
Head
the output matrix that turns the last hidden state into token scores.
K4 and K6
quantized formats at about 4 and 6 bits per weight (BF16 holds 16).
K3.25
a checkpoint of the same model in the same family of formats, with routed experts at about 3.25 bits per weight and an FP8 core, measured here on 2026-10-26 on an earlier engine release (CuteAFD v3.0.1); in the distance tables it is a row for scale, not part of that comparison. Since this was written the checkpoint has become a fifth configuration, k325-fp8, on v5.0.0 (bits per weight); its passes are running.
FP8 settings
the engine has three FP8 conversion settings (GLM5_FLASH_KDA_FP8, GLM5_FLASH_FP8_HEAD, GLM5_FLASH_FP8_PREFILL). anchor is launched with all three off, which keeps its BF16 core matrices and head at BF16. As logged at load, KDA FP8 reads Off in all 9 serving launches of the three probe arms; the FP8 prefill setting reads none in anchor and [Mla, Ffn] in hqa and compact; the head reads BF16 in anchor and K6 in the other two. Switching the prefill setting off on hqa left every recorded distribution bit-identical in a check before the graded runs.
Passes and pass sets
a pass is one run of a configuration's 240 requests (60 items at four lengths). Passes 1-2 are the frozen two-pass result, passes 3-4 were added under amendment 1, and "four passes" pools them.
HQA
the checkpoint that carries BF16 copies of two attention projections (q_b_proj, o_proj) beside its K6 core; ATTENTION_MODE selects which copies run.
Field score (task score, the partial-credit score)
the share of a reply's eight answer fields that are right, 0 for a reply that did not finish; higher is better, and one point is 0.01.
Every field right (the strict measure)
the count of replies with all eight right.
Weights outside the experts
what the engine's startup plan places on the two GPUs outside the experts: the 45 layers' weights (one copy on each GPU; the load line's "coordinator weights"), the output head and the token embedding table (each on one GPU). In the three probe arms those parts add up to the plan's figure; in exlr8-k4 the plan's figure is 505 MiB more than they add up to, and the logs do not itemize that remainder. The count of 45 layers is the engine's load line; the HQA checkpoint holds 46 BF16 o_proj matrices (layer indices 0 to 45) and 12 q_b_proj. Both counts are as read, from different sources.
Resident weights
everything held as weights on the two GPUs after load, experts included. The part that is not weights outside the experts is the same in the three probe arms (150,888, 150,886 and 150,886 MiB) and 154,585 MiB in exlr8-k4, which brings its own experts; that is why its resident total is not the smallest although its weights outside the experts are.
Left under the memory cap
the engine's per-GPU memory cap minus weights, workspaces, reserve and KV pool.
Workspaces and reserve
two items of the engine's admission line beside weights and KV pool, per GPU; read from each launch's log, not measured here.
KV pool
the tokens of attention cache the engine admits for all simultaneous requests together.
Depth profile and scoring capture
two exploratory readings of given text, scored position by position with nothing sampled; the first ran before the graded runs, the second after them with the reference checkpoint. Their launches are the scoring launches.
KL
how far a configuration's next-token probabilities are from the BF16 model's at the same position; the fidelity set computes it over the reference's top 1,024 tokens plus one term for the rest, the teacher panel over the full vocabulary.
Generated positions
the scored positions the fidelity set marks as generated text (15,104), as opposed to context; its figures here are over those.
Where BF16 is confident
positions where the BF16 model gives its most likely token a probability of at least 0.5.

Limits: one model family; one engine release; synthetic tasks; 60 items per length; K4-class checkpoints only; BF16 reference to 14.4K only.

Distance from the BF16 model

Status: descriptive; no gate and no ranking rule; every interval computed is listed. Ran 2026-11-12 04:06 to 05:28, one engine at a time, every step exit 0. Open questions

  • Where does the long-context loss that every probe arm shows, anchor included, come from? The arms share the model, the K4 experts, the engine, the drafter, the sampling settings and the reply cap; a third to a half of the loss is replies that did not finish.
  • Is the K6 core's nominal gap on long-context running totals (ledger at 64K and 127K) real? Twenty items leave both zero and a loss of about 0.13 in field score inside the pooled interval.
  • Is a conversation continued on history the model itself wrote equivalent to the same tokens prefilled? The eight-turn pass did not test this.
  • Dated 2026-11-12, on the first question: over four passes a fall of about 0.06 from 4K to 127K is common to the four configurations, exlr8-k4 included. No unquantized model and no other engine ran these tasks, so where it comes from is still open.
  • Dated 2026-11-12, on the second question: the nominal gap did not repeat. On ledger at 64K + 127K, compact − anchor was −0.062 [−0.128, +0.002] in passes 1-2, +0.011 [−0.055, +0.072] in passes 3-4 and is −0.026 [−0.070, +0.019] over four (Four passes).
  • Added 2026-11-12: is compact's lower score at 127K real, and does it come from replies that do not finish, from wrong fields in replies that do, or from one task family? Over four passes it is indicated, not established, and the two pass sets disagree on each of those splits (Four passes). Reproducing this

  • Recompute. In the results folder, python3 analysis/posthoc.py (standard library only) rebuilds the scores, differences and intervals on this page from samples.csv and writes POSTHOC.json; python3 tools/verify.py at the repository root checks docs/findings.json against the same table. Run from a clean copy of the published folder on 2026-11-11: same output.   • Rebuild the inputs. drivers/gen_tasks.py --items 20 --first 100 regenerates the 240 rendered items from their seeds; it needs the tokenizers package and the model's tokenizer.json (set the path at the top of the script; its SHA-256 is checked). items/measured/index.json lists the SHA-256 of every rendered item. Regenerated from the published script on 2026-11-11: 240 of 240 hashes match.
  • Re-measure. chain.sh, drivers/run_tasks.py and configs/ are what ran, with the image digest and checkpoint revisions in RUN.json. The HQA checkpoint is no longer on the hub, so hqa and compact cannot be re-measured without a copy of it; anchor's checkpoint is assembled locally, with every core matrix taken from the original BF16 weights, and was never a release.
