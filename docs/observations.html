Observations and confounds

Behaviour differences between the two stacks, each with how it is known, and what else differs and how each block handles it.

The differences a user notices first: CuteAFD honours "thinking off" and the vLLM fork does not; CuteAFD reuses repeated prompts from its cache and the vLLM fork only in whole 4,352-token blocks; CuteAFD is ready in about 1.5 min and the vLLM fork in about 6.4 min with its JIT caches persisted on this setup (11.6 min without), which matters when switching models; the vLLM fork's long prefill is not bit-reproducible run to run, CuteAFD's is.

Observations in detail

Each item is the behaviour as measured or as read in source, with how it is known. None is a claim about output quality.

  • Thinking off: the two stacks render different prompts (prompt measured with one request; parser behaviour read in source). The checkpoint's chat template, byte-identical on both stacks, has no thinking switch and always ends with <|assistant|><think>. CuteAFD renders enable_thinking: false as an empty <think></think> (one more prompt token). vLLM renders the same prompt with the flag on or off (147 prompt tokens both times), and with it off its reasoning parser returns the generated reasoning as content. Thinking off would therefore give the two engines different prompts and different generated content, so every generation request in Blocks T and L runs with thinking on.
  • Control-token strings in user text (measured in Block T). The 128K code prompts contain literal <think> and </think> strings; the vLLM stack parses them as control tokens, CuteAFD keeps them as text, so those prompts are 24 tokens longer on CuteAFD.
  • vLLM's multi-chunk prefill is not run-to-run deterministic (measured, Block Q captures, each run alone on the server). Rows inside the first 2,045-token prefill chunk are bit-identical between runs; rows beyond it almost never are. CuteAFD's repeats are byte-identical. CuteAFD is therefore compared with the mean of three vLLM runs from two launches.
  • vLLM prefix-cache reuse is in whole 4,352-token blocks, without the last two blocks of a prompt (measured, F2): repeated prompts of 1K to 8,704 tokens got 0 cached tokens; a 17,408-token prompt got 4,352, then 8,704. The server log shows the MLA cache groups at block size 4,352 in align mode. The v0.9.0 opt-in boundary lookup (GLM53_DFLASH_BOUNDARY_LOOKUP, default 0) was not tested. CuteAFD restored a repeated 8K prompt in 0.017 s.
  • Startup time, which is the cost of switching models (measured from server logs: results/2026-10-27-vllm-startup-cache). CuteAFD v3.0.1 is ready in 89 s: its kernels are compiled ahead of time and shipped in the image (PROGRAMS.json), so there is no startup JIT; its CPU planner computes the memory layout up front, so there is no profiling pass; and the experts load through a parallel shared read in 30.6 s. On this setup, the container keeps ~/.cache between starts but not the TileLang, Triton, TorchInductor and CUDA kernel caches, so the vLLM fork v0.9.2 compiled 49 TileLang kernels at every start and was ready in 697 s (11.6 min). On this setup, persisting those caches (pointing TILELANG_CACHE_DIR, TRITON_CACHE_DIR, TORCHINDUCTOR_CACHE_DIR and CUDA_CACHE_PATH into the cache directory the container already keeps) brings it to 382 s (6.4 min, −45%):

The first start after the change fills the caches and takes 714 s; later starts are warm. What remains is mostly weight loading (about 4 minutes including loader overhead). Other projects keep these caches between starts the same way (blackwell-llm-docker#73, which reports about 3.2 min of TileLang compiling per restart; sglang#39364; vLLM's Docker guide mounts the Hugging Face cache and ~/.cache/vllm).

  • CuteAFD's P-B difference at 8-16K and its FP8 switches (measured, F1, prefill-shaped scoring). Switching prefill GEMMs from W8A8 to W8A16 moves the 8-16K KL most; with KDA projections, head and prefill all switched, no difference from vLLM is resolved, at about 4% median decode cost. Decode-shaped precision was not scored. The difference is concentrated in block B (long code reading), so length and content are not separated. CuteAFD's distributions are flatter there (entropy 0.580 against vLLM's 0.523, higher in 18 of 18 windows; read from the dumps by the audit).
  • CuteAFD's launcher defaults (read in the launcher). Output limit 4,096 tokens, which clamps longer requests (the runs here set MAX_OUTPUT_TOKENS=393216; with it, a 12,000-token request ran to its max_tokens, measured); request logging on unless USAGE=off; listen address 0.0.0.0 under host networking unless ADDR is set; the coordinator launch passes --device=/dev/infiniband, which Docker requires to exist (the runs here pass it only when it exists, in the same form as the repository's wip.sh: repro/cuteafd/patches/).
  • CuteAFD's swiglu_limit is a compiled constant (read in source): 10, which equals this checkpoint's declared value, so these runs use the declared clamp. The value in config.json is parsed but not compared with the constant.
  • CuteAFD's router logits differ slightly between its two GEMM routes (measured on one GPU, exploratory): across the 160/161-row switch 0.36% of logits are bit-equal, the largest difference is 8.2e-5, and the top-8 expert set differs in 2 of 64,000 rows; within each route the logits do not depend on the row count, and decode steps stay on one route. This is numerical variation between routes, the same kind as observed on the vLLM engine: results/2026-10-26-e1-router-route.
  • Draft acceptance (measured on vLLM, drift subset): 1.53 of 3 drafted tokens accepted per verify step (51%). CuteAFD drafts adaptively and exposes no acceptance counter on its API.
  • Earlier vLLM-engine items D1-D7 in CuteAFD (read in source, not measured): the source audit maps the seven items from earlier evaluation (five of them addressed in tpurtell's v0.9.2) onto CuteAFD. For four, CuteAFD covers the same case in its own code; three do not arise in its design: results/2026-10-26-cuteafd-setup-checks.
